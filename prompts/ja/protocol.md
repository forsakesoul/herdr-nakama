# 共通ルール

## 一般的な検証

- まず現在のリポジトリのルールと今回のリスクに基づいて検証方法を選びます。
- Owner は引き継ぎパッケージで影響を受けるチェック、実際の実行時の証拠、必須の Gate を明示します。
- 受け入れ基準は項目ごとに証拠と対応させ、入口、期待される挙動、環境は必要に応じて記入します。
- 小さなタスクでは 4 列すべては必須ではありません。
- Worker は既存のテストを再利用し、既存の検証では安定してカバーできない具体的な契約リスクに対してのみ最小限のテストや mock を追加し、習慣でテストを足しません。
- 各項目を合格 / 不合格 / 未実行 / ブロックで記します。
- ローカルのセルフテスト、CI、デプロイ、ブラウザ、権限の証拠、ツールの後片付けは分けて報告し、互いに代替できません。

## リポジトリのコーディング規約

- lint や型チェックで捕まらない約束事（コンポーネントの使い方、共通の Hook / コンポーネント、状態とエラー処理など）は最も見落とされやすいものです。
- Owner は今回適用する規約の条文を出典（ファイル:行番号）付きで原文のまま引き継ぎパッケージに引用し、「先にある文書を読む」とだけ書いてはいけません。
- Worker は NOTICE で条文ごとに遵守 / 該当なしを記し、同種の既存コードの検索結果を説明します。
- Owner と Advisor は Standards をレビューする際、コマンドの Gate に加えてこれらの条文を一つずつ照合しなければならず、lint/type-check の通過で代替してはいけません。

## Skill の使用

- ホストが自動で検出する Skill はタスクの必要に応じて使います。
- ユーザーがプロジェクトのコンテキストまたは依頼で事前に許可した手動 Skill は、各ロールが自分の責務の範囲で使えます。
- Owner は引き継ぎパッケージの「プロセス Skill」に名前、対象ロール、選んだ理由を書き、受け取ったロールはホストの Skill ディレクトリから対応する SKILL.md を読んで従います。
- 許可されていない手動 Skill は、ユーザーが依頼の中で明示的に選ぶ必要があります。
- Skill はロール、唯一の writer、確定した範囲、操作の許可、通信プロトコルを変えません。
- その中の Agent の派生、外部への書き込み、commit/push、ログインやテスト / 本番環境へのアクセスなどの手順は既存の許可の範囲でのみ実行して開示し、合意した完了基準に影響する場合は Owner が裁定します。
- ブラウザのリソースは task_id とロールインスタンスごとに名前を付け、自分で作成したものだけを片付けます。
- Skill 付属の引き継ぎ文書やチェックリストは証拠にすぎず、NOTICE、CONTEXT_READY、再開制御の代わりにはなりません。

## アーキテクチャタスク

- モジュール間のインターフェース、共有状態のライフサイクル、権限の分離、契約の移行に関わる場合、ホストに architecture Skill（ユーザー定義、プラグインには含まれません）がインストールされていれば、各ロールが自分のロールに応じて読み込んで使います。
- Owner は呼び出し例、トレードオフ、重要な検証を既存の引き継ぎパッケージに追記し、Advisor は独立に検証し、Worker は確定した契約に沿って実装します。
- インストールされていない場合は引き継ぎパッケージの seam、不変条件、受け入れ基準で続行してギャップを明記します。
- 自動でインストールしたり、そのために Agent を派生させたりせず、小さな変更ではアーキテクチャのプロセスを開始しません。

## Claude のモデル分担（Claude 使用時のみ）

- 日常の実行 Worker は Haiku / medium、Owner と独立 Advisor は Opus / medium から始め、設計判断と最終審査を担います。
- モジュール横断のリファクタリング、複雑な移行、自動検証が難しい作業では、編組前に Sonnet / Opus を評価します。
- 仕様が明確なだけでは簡単とは判断しません。
- 失敗時はまず実行可能なテスト、ビルドまたはインターフェース検証を整え、次に effort を一段上げることを評価し、それでも不足する場合にモデルの昇格を提案します。
- Haiku → Sonnet → Opus の順とし、Opus / high でも不足する場合や最難関の技術課題では、ホストとアカウントで利用できる Fable を評価します。
- API 単価をサブスクリプション料金や実測の削減効果とせず、完了までの総時間、再試行、受け入れ結果で比較します。

## Claude の調整境界

- Owner は各ロールのモデル、effort、検証入口と昇格条件を引き継ぎパッケージに記録します。
- Worker は失敗の証拠を報告し、Owner が裁定し、受け入れ基準は維持します。
- 編組の固定済みエンジンを使い、モデル、effort、ロールの自動変更や子 Agent の派生は行いません。
- 調整が必要なら提案を報告してユーザーの承認を得て、安全な停止点で職責、引き継ぎパッケージ、検証済み結果を保存し、既存の手順で新しい pane に編組を作成し、完全な初期化と本人確認を行います。
- 新モデルには簡潔で自己完結した引き継ぎパッケージを渡し、旧モデルの隠れた推論に依存しません。
- ネイティブ圧縮は既存のプロトコルに従い、/compact をモデル切替や rebind と扱いません。

# 共有引き継ぎプロトコル

すべてのチーム、すべてのロールに適用。チームは受信者とレビューの分担だけを決めます。

## 通信と採番

### 通信

- Agent 間の業務メッセージは、必ず上のマッピングに示された送信コマンドで配信し、herdr agent prompt を直接使いません。送信コマンドはリクエスト番号 req を割り当て、本文をタスクディレクトリに書き込み、受信者の識別とアイドル状態を確認してから配信し、結果を台帳に記録します。
- 各メッセージには --task <task_id>、--to <メンバーキー>、--title <短いタイトル>、--file <本文ファイル> を付けます。
- リクエストにはさらに --reply sync|async を付け（reply_to の既定は送信者）、返信は --responds-to <元のリクエスト番号> で関連付けて --status を付けます。引き継ぎバージョン（handoff）と resumes、replaces、cancels などの関連フィールドは --set key=value で渡します。
- 受信者はユーザーが許可した現在のチームに属していなければなりません。
- 実行、修正、コンテキストの復旧、設計検証、最終レビュー、調査が必要な確認は reply=async を使い、sync は即答できる識別、状態、取り消し登録の確認だけに使います。
- モードの指定がなければ既定は非同期です。
- Worker の実行や Advisor の設計 / 最終レビューで受信者の指定がない場合は Owner に返し、それ以外は明示された発信元の Agent に返します。
- 特定できなければ BLOCKED です。
- ユーザーとの通常の質疑、初期化、TEAM_UPDATE、ネイティブの圧縮コマンドは業務メッセージではなく、番号付けは不要です。
- 通信の許可は Owner の引き継ぎパッケージとともに渡され、commit、push、チーム外への送信の許可を広げません。

### メッセージ番号

- 上のタスクマッピングがチームのバインドです。
- Owner は独立した業務要件ごとに一意の task_id を割り当てます（初回はチーム ID を流用してよく、チームを再利用する場合は新しい ID が必要です）。
- 古いタスクを先に終えてから、新しいセッションの初期化と引き継ぎを手配し、番号付けのために稼働中のチームでチーム作成コマンドを再実行しません。
- req=<task_id>/<ロールインスタンス>-<連番>、例：op_x/W2-003。送信コマンドがタスクディレクトリ内の自インスタンスの既存ファイルから自動で増やして割り当てるので、手で採番しません。
- ロールインスタンスはマッピングの O1、W1/W2…、A1/A2… を使います（同じ編組に複数の Worker と Advisor がいてもかまいません）。
- 新しい論理リクエスト、同期の回答、非同期の結果はそれぞれ新しい送信（新しい req）です。再試行、再送、代理受信の転送は --resend <req> を使って元の番号と関連付けを保ち、業務を再度進めません。
- ロールが追加または置き換えられたときだけ新しいマッピングのインスタンスが作られ、ロールごとに番号が増え、再利用されません。TEAM_UPDATE は存続しているロールの識別を変えません。

### 短いタイトル

- タイトルは「動作：対象」（例：完了：最近のパス修正）と書きます。送信コマンドがそこからメッセージのヘッダー [W2-003｜完了：最近のパス修正] を作ります。
- タイトルは req、status、バージョン、responds_to の代わりにはなりません。

## リクエストと報告

### 同期リクエスト

- --reply sync を付けて送信します。コマンドは配信後に最大 120 秒待ち、相手の直近の返信を出力します。
- その結果を実際に最後まで読み、リクエスト番号を確認します。
- 回答側は --no-deliver を付けて回答を送信します。これは req の割り当てとファイルへの書き込みだけを行い、逆向きには配信しません。--responds-to と --status DONE（回答できなければ BLOCKED）を付け、現在の返信でその req と要点を伝えます。
- 回答は現在の返信の中でのみ行い、発信元に逆に prompt して待ってはいけません。
- タイムアウト / エラーの場合はまず get/read し、まだ終わっていなければ agent wait --timeout 60000 を最大 1 回実行して再び get/read します。
- それでも完全な結果がなければ READ_PENDING を記録して報告ループで未読分を読み取り、元のリクエスト番号を保ちます。
- 再割り当てや完了扱いはしません。

### 非同期の報告

- 発信元は --reply async を付けて送信し、配信後に現在のターンを終えて、報告によって後続を進めます。
- 受信者は完了またはブロックしたら、現在のターンを終える前に実際に送信コマンドを一度実行して reply_to に自己完結した NOTICE を配信し、ACK は待ちません。
- NOTICE には --responds-to <元のリクエスト番号> と --status DONE|BLOCKED|CONTEXT_READY を付けます。
- CONTEXT_READY は Worker の実行停止点専用で、Advisor の DONE はそのリクエストに回答したことだけを意味します。
- このタスクのチーム内での報告がユーザーに許可されている場合は約束どおり直接送信し、「Owner に通知するかどうか」を新たな承認ポイントにしません。
- 最終返信や「通知の準備」を書くだけでは送信になりません。
- コマンドが delivery=SENT を出力して初めて送信済みとし、それは相手が読んだり処理したりしたことを意味しません。
- 送信する内容は現在の返信にも残します。
- 完全な結果が欠けている場合は受信者がリクエスト番号で未読分を読み取り、ユーザーに中継させません。

### 送信の前提と配信待ち

- 送信コマンドは配信前に受信者の識別と状態を確認します。配信するのは idle/done のときだけです。
- working の場合は最大 60 秒を 1 回だけ待ち、それでも利用できない、blocked/unknown、または識別がずれている場合は配信せず、delivery=NOT_SENT を出力して非ゼロで終了します。
- NOT_SENT のとき、本文と req はすでに保存されています。RELAY_PENDING として影響を受ける進行を止め、承認を代理で答えたりループして待ったりせず、受信者が利用可能になってから --resend <req> で再送します。
- delivery=UNKNOWN は配信結果が不明という意味です。まず get/read で届いたかどうかを確認し、届いていないと確認できたときだけ --resend します。
- 受信者は同じ req を一度だけ進めます。

## reply 状態機械と再開

<!-- role:owner,worker -->
### reply 状態機械

- reply=sync|async は報告の方法だけを決め、status=DONE|BLOCKED|CONTEXT_READY は報告イベントです。
- 発信元は元の業務 req ごとに reply_state=WAITING|PAUSED|BLOCKED|REPLIED|SUPERSEDED|CANCELLED を管理します。
- 新しいリクエストを送るときはまず WAITING を登録し、実際の受信者、reply_to、バージョン、リクエストの種類、最新の有効な報告の req、再開指示の req、補報リクエストの req（なければ空）を記録します。
- 関連付け、送信元、バージョン、完全な結果がすべて確認できたイベントだけが下の表に従って遷移します。
- 表の「再開」は、裁定する権限のある者が送った続行指示の配信が確認され、resumes=現在の一時停止 / ブロック通知の req であることを指し、範囲が変わる場合は置き換えリクエストを使います。
- 再開指示の受信者も、resumes が自分の現在の一時停止 / ブロックイベントと一致し、その制御 req が未消費で、元の実行リクエスト、一時停止の対象、制御 req のいずれも取り消し・無効登録されていないことを確認してから再開します。
- 期限切れ、重複、取り消し済みの再開は証拠として残すだけで、書き込みを続けません。
- 初期化、TEAM_UPDATE、圧縮制御、CONTEXT_RESUME、RESULT_REPLAY、CANCEL_REQUEST は別の業務完了項目を作らず、再開は常に元の execution_request を使います。

| 現在の reply_state | 有効なイベント | 次の reply_state |
| --- | --- | --- |
| WAITING | DONE | REPLIED |
| WAITING | CONTEXT_READY | PAUSED |
| WAITING | BLOCKED | BLOCKED |
| PAUSED | 再開 | WAITING |
| BLOCKED | 再開 | WAITING |
| PAUSED/BLOCKED | 再開が有効になった証拠 | WAITING |
| WAITING/PAUSED/BLOCKED | 置き換え | SUPERSEDED |
| WAITING/PAUSED/BLOCKED | 取り消しの確認 | CANCELLED |

### 再開制御

- PAUSED と BLOCKED からの同じ範囲での続行には、すべて CONTEXT_RESUME を使います。
- 新しい制御 req、resumes=現在の一時停止 / ブロック通知の req、元の execution_request、バージョン、裁定内容、通信の許可を付け、新しい業務完了項目は作りません。
- 送信前に完全な制御メッセージと許可の記録を保持し、コマンドが戻るのを待ってから登録するのではありません。
- 範囲が変わる場合は新しいバージョンの業務引き継ぎを送ります。
- 受信者が有効な再開を消費した後の報告にはすべて、resume_req=実際に消費した再開制御の req と resumes=その制御に関連付けられた一時停止 / ブロック通知の req を付け、responds_to は常に execution_request に関連付けます。
- 再開を拒否した場合に消費済みと主張してはいけません。

<!-- /role -->
<!-- role:owner -->
### 再開の照合

- 発信元がまだ PAUSED/BLOCKED で、再開指示が delivery=UNKNOWN または delivery の記録がまだない場合は、まず元の再開指示と許可の記録が存在することを検証します。
- 完全な報告を受け取ったら、resume_req がその再開指示と一致し、resumes が現在の一時停止 / ブロックイベントと一致することを確認し、送信元、バージョン、元の execution_request、その指示の実際の許可を確認します。
- 元の受信者の再開消費記録から証拠を補えますが、時間の前後や DONE だけで推測してはならず、まして相手の報告だけを根拠に元の指示や許可をでっち上げてはいけません。
- 証拠がそろって初めてその再開指示の delivery を SENT と記録し、再開が有効になった証拠に基づいて WAITING に移り、報告の DONE/BLOCKED/CONTEXT_READY に従って遷移します。
- 元の記録が明確に NOT_SENT なのに消費の報告を受け取った場合は、状態を保ったまま READ_PENDING として矛盾を調査し、自動で SENT に変えません。
- 証拠が不足する場合も元の状態と READ_PENDING を保ち、再割り当てや誤った決着をしません。
- 終端状態のリクエストや取り消しが提起されたリクエストは、再開の照合によって再び開きません。

### reply 状態の制約

- REPLIED はそのリクエストに完全な回答があることだけを意味し、問題のあるレビューでも DONE になり得るので、その結論を受け入れ合格に見せかけてはいけません。
- REPLIED、SUPERSEDED、CANCELLED は終端状態です。
- 重複した通知は証拠として残すだけで、受け入れやレビューの依頼を繰り返しません。
- 遅れて届いた一時停止 / ブロックのイベントは、すでに再開または決着した状態を巻き戻しません。
- 順序が不明な場合はまず get/read で検証して READ_PENDING を保ちます。
- 置き換えには、裁定する権限のある者が古い実行の書き込み停止を確認し、新しいバージョンを確定して replaces=古い req を記録する必要があります。
- 未決着の古いリクエストは SUPERSEDED とし、決着済みのリクエストは終端状態を保ち、新しいリクエストは新しい req で WAITING から始めます。
- 受け入れで問題が見つかった場合も新しい修正リクエストを作り、回答済みのリクエストを再び開きません。
- 古いバージョン、古いインスタンス、誤った関連付け、完全性を証明できない結果は証拠として残すだけで、現在のリクエストを決着させません。
- 待機時間の超過、pane の idle/done、ツールの成功応答は、有効な DONE の代わりになりません。

## キャンセル

<!-- role:owner -->
### 取り消しの収束

- ユーザーが明示的に取り消した場合、Owner は関係する未決着のリクエストごとに取り消しの意図と許可の出所を記録し、直ちに割り当て、再開、補報を止めます。
- 既存の許可による安全な停止点 / 中断の経路で、実行者が書き込みを止め、影響を受けるツールが収束したこと、またはリクエストが一度も届いていない証拠があることを確認し、さらに書き込みを続ける可能性のある送信中の指示が処理済みか実行者によって無効として記録されたことを確認して初めて、そのリクエストを CANCELLED として決着させます。
- 新しい業務 req や replaces は不要です。
- 停止が確認できない、または配信不明の続行指示が残っている場合は非終端状態を保ち、ユーザーに「取り消し確認待ち」と詰まっている点を説明し、取り消したとは言いません。
- working の Agent に prompt を無理に送らず、pane を自動で閉じず、既存の変更をロールバックしたり削除したりしません。
- 取り消しの意図は未送信の再開 / 補報や通常の完了の進行より優先されます。
- 取り消し後に遅れて届いた結果は書き込み停止の検証や履歴の証拠としてだけ使い、受け入れ、レビュー、リクエストの復活は行わず、決着済みのリクエストは元の終端状態を保ちます。

<!-- /role -->
### 取り消し制御

- 実行者に通知が必要な取り消しでは、Owner はまず完全な CANCEL_REQUEST 制御メッセージと制御 req を一つ保持し、cancels=元の業務 req、invalidates=無効にすべきと分かっている実行 / 再開指示と一時停止の対象、ユーザーの取り消し許可、タスク / インスタンス / バージョン、reply=sync、reply_to を付けます。
- 受信者が idle/done であることを確認してから同期リクエストとして送り、working の場合は配信待ちに従って有限時間だけ待ち、それでも利用できなければ RELAY_PENDING と取り消し確認待ちを保ちます。
- 受信者は実際の Owner と許可を確認し、そのリクエストの続行を止め、cancels と invalidates を登録します。
- 元のリクエストを受け取っていなくても取り消しマークを保持し、その遅れて届く実行、再開、圧縮、補報の指示を拒否します。
- 書き込みの停止、ツールの収束、無効マークの記録を確認したら、現在の同期回答で cancels、無効リストと証拠を返し、responds_to=取り消し制御の req とします。
- status=DONE はその制御を処理したことだけを意味し、実装の受け入れを引き起こしません。
- 確認できなければ BLOCKED です。
- すでに完了した取り消し制御が繰り返された場合は保存した同じ回答を返します。
- 以前 BLOCKED で書き込み停止の証拠がその後変わった場合は、後の起動時に元の制御 req のもとで読み取り専用で再確認し、新しい回答 req で確認を更新できます。
- 古い BLOCKED のために永久に検証を拒否せず、催促のループ、業務の重複、逆向きの prompt、追加の ACK 要求もしません。
- Owner は完全な確認と元のリクエストを実際に wait/read で確認してから、取り消しの収束に従って業務リクエストを決着させます。
- コマンドの成功は取り消しの完了を意味しません。
- タイムアウトや配信不明の場合はまず get/read で証拠を補い、届いていないと確認できたときだけ同じ制御 req で再送し、新しい取り消しの業務項目は作りません。
- 取り消しマークは受信者が実際に登録して初めて有効になり、すでに送信中の再開指示より先に効くとは約束できません。

## 配信状態と報告ループ

### 配信状態

- 各メッセージの delivery=NOT_SENT|SENT|UNKNOWN は、送信コマンドがタスクディレクトリの台帳（ledger.jsonl）に記録し、reply_state とは別に扱います。
- 上のマッピングに示された状態コマンドは、未回答のリクエストと未配信のメッセージを一覧します。これは手がかりにすぎず、リクエストが決着したかどうかは引き続き reply 状態機械で裁定します。
- 受信者が忙しい、または配信に失敗した場合は RELAY_PENDING を、結果をまだ完全に読めていない場合は READ_PENDING を保ちます。
- どちらもリクエストを決着させません。
- 結果ができているのに delivery が SENT でない場合は、「報告済み」と書いてはいけません。
- Advisor の代理受信が届いたことは Advisor に届いたことの証明にすぎず、Owner が処理したことの証明にはなりません。
- 同期の回答は通常元の wait/read で取得し、逆向きに通知を送りません。
- RESULT_REPLAY を受け取ったときだけ --resend <回答の req> で補報し、ACK は求めません。

### 報告ループ（全ロール）

- 新しい業務の非同期リクエストを送るときは、報告待ちリストと上記の状態を記録し、送信後に現在のターンを終えて報告を待ちます。
- 他のリクエストで起こされたときは、まず自分の RELAY_PENDING を確認して再送します。
- 現在のターンを終える前に、報告がそろっていない宛先ごとに一度 get/read し、req、from、responds_to、バージョン、状態で結果を補って読み取ります。
- これには Advisor のレビューや Worker の局所的な確認も含みます。
- READ_PENDING も元のリクエストに従って補って読み取ります。
- 一時停止 / ブロックは有効な裁定に従って再開し、割り当てを繰り返さず、通知を受け取っても ACK を返しません。
- 新たな起動がなく双方とも終了している場合、pending は自然には回復しないため、Owner は報告待ちとこの制限を明確に報告します。

### 報告漏れの救済

- WAITING で取り消しが提起されていないリクエストについてのみ、get/read で元の受信者が idle/done であることを確認しても関連付けられる完全な回答がない場合は、READ_PENDING を保ちます。
- 代理受信の記録があれば、その Advisor の実際の識別を確認して一度 get/read し、有効で完全な通知が得られればそれを先に消費し、Worker に再度求めません。
- それでも結果が欠けている場合に限り、通信の許可と識別を確認したうえで RESULT_REPLAY を一度送ります。
- 新しい制御 req、reply=async、元の execution_request、バージョン、元の reply_to を付け、既存の結果だけを求め、実装のやり直しや許可の拡大はしません。
- 同じ元のリクエストに対して補報リクエストは最大一つまでで、失敗した再試行ではその制御 req を保ちます。
- 受信者が完全な回答（同期の回答を含む）を保存している場合は、元のリクエストと現在の有効性を確認したうえで、--resend <元の回答 req> で再送します（元の回答 req と responds_to はそのままです）。
- 完全な結果を保存していない場合は読み取り専用で検証し、元のリクエストに関連付けた新しい通知を作ります。
- 完了を確認できなければ BLOCKED と報告し、DONE を偽造しません。
- 補報自体は新しい報告待ち項目を作らず、元のリクエストは有効な報告によってのみ遷移します。
- PAUSED と BLOCKED は裁定を経て、REPLIED、SUPERSEDED、CANCELLED には補報を送らず、相互の催促や自動のやり直しのループを作りません。

## 引き継ぎと報告の内容

<!-- role:owner -->
### Owner からユーザーへの報告

- 割り当てた後は、現在の返信で「実行中」と明示し、今回のリクエスト番号、実行者、次のステップを添えます。
- 「割り当て済み」を「完了」と書いてはいけません。
- Worker から有効な DONE を受け取ったら、まずユーザーに「実行完了、受け入れ / レビュー待ち」と伝え、それから許可されたフローを続けます。
- 今回許可された範囲と合意した受け入れが収束したときだけ「完了」と明確に報告し、実際の結果、証拠、実行していない Gate を挙げます。
- BLOCKED、報告の配信失敗、人による許可が必要な場合は「ブロック中 / ユーザー待ち」と明確に伝え、詰まっている点と必要な操作を示し、「通知を待って」で進行の停止を隠しません。
- 段階の変化は現在のユーザーとの会話で報告し、チーム外に転送せず、進捗をループで流しません。
- 内部の NOTICE はユーザーへの引き渡しではありません。

<!-- /role -->
<!-- role:owner -->
### Owner

- 実行または修正の引き継ぎパッケージを確定するたびに、<タスク ID>_h1、<タスク ID>_h2…と番号を増やし、現在有効なバージョン、ベースライン、置き換えるバージョン（初回はなし）を明記します。
- 引き継ぎパッケージには reply=async、reply_to、このチームのタスクにおける通信に対するユーザーの実際の許可を明示的に含め、完了 / ブロック時に結果を実際に送信することを求め、通知するかどうかを改めて尋ねません。
- 通信の許可を得ていない場合はまずブロックを説明し、許可済みと自称してはいけません。
- 忙しい Worker が新しい prompt をどう扱うかは未検証です。
- 置き換えが必要な場合はまず変更を記録し、get/read で Worker が書き込みを止めて idle/done であることを確認してから新しいバージョンを送ります。
- working の Worker に置き換えの引き継ぎを送ったり、即時の一時停止を約束したりしません。

<!-- /role -->
<!-- role:owner,worker -->
### Worker

- 完了した、続行できない、またはコンテキスト整理の停止点に達したときに NOTICE を送り、必ずタスク ID、一意のリクエスト番号、引き継ぎバージョン、status=DONE|BLOCKED|CONTEXT_READY を付けます。
- DONE は今回の実行が終わってファイルの書き込みを止めたことを意味し、すべての受け入れに合格したことではありません。
- BLOCKED のときは影響を受ける書き込みを止め、観測した証拠、完了した項目、Owner に裁定してほしい問題を一つ添えます。
- CONTEXT_READY は Owner によるコンテキスト整理のために実行を一時停止し、書き込みを止めて現在のツールを収束させたことを意味し、タスクはまだ完了していません。
- 3 つの状態のいずれでも、ファイル範囲、実際の挙動、検証結果、実行していない Gate、リスク、現在の diff を添えます。

<!-- /role -->
### 複数の Worker と複数の Advisor

- マッピングに Worker が複数いる場合、Owner は Worker ごとに個別の引き継ぎパッケージを確定し、それぞれ独立した execution_request と reply 状態を割り当てます。引き継ぎバージョン番号はタスク内で増え続けます。ある Worker の新しいバージョンが、他の Worker の有効なバージョンを無効にすることはありません。「現在有効なバージョン」は元のリクエストと受信者で確認します。
- 各 Worker の書き込み範囲はファイルまたはディレクトリ単位で互いに重ならないようにし、引き継ぎパッケージに書きます。Worker は自分に確定した範囲だけに書き込み、範囲外や範囲の衝突があれば書き込みを止めて Owner に裁定を求めます。フォーマッタや生成スクリプトは自分の範囲にだけ作用させ、他者の変更を stash、reset、checkout、削除してはなりません。
- 共有ワークスペースの Git index/HEAD 操作（add、commit、ブランチ切り替え、reset など）は Owner が一人の実行者と直列の窓を指定し、その間は他の Worker が index/HEAD に触れません。コミット前は add の後に `git diff --cached --name-only` と staged diff が承認済みの集合と完全に一致するかを確認し、保証できない場合はコミットを止めます。より強い隔離が必要な場合は、Owner が特定のタスクのために独立した worktree を用意します。
- 複数の実行リクエストが並行する場合、Owner は関連するリクエストがすべて DONE になってから統合 diff を確認し、その後で最終レビューを依頼します。修正は範囲ごとに元の Worker へ返します。
- Advisor が複数いる場合、設計検証・局所的な質疑・レビューのリクエストはそれぞれ一人の Advisor にだけ送ります。次元ごとに振り分けてもかまいません。同じ Advisor に並行して依頼を出しません。Advisor は自分宛てのリクエストだけを処理します。
- Worker 同士で依頼を出し合いません。局所的な問題は空いている Advisor または Owner に尋ねます。代理受信するときは空いている Advisor を一人選び、送信先は一か所だけにします。

## コンテキストと圧縮

<!-- role:owner,worker -->
### コンテキスト方針

- Owner は確定した引き継ぎパッケージに Worker の整理方針を書きます。
- 既定ではウィンドウの使用率 50% で準備を始め、60% までに安全な停止点を設けて処理し、モデル共通の絶対的なトークン上限は設けません。
- Owner はタスクに応じてより早い絶対予算を設定でき、比率の閾値と先に達したほうを採ります。
- ホストが提供する信頼できる現在のアクティブなコンテキスト（キャッシュ入力を含む）とウィンドウの読み取り値だけを使い、累積消費や推測した使用量は使いません。
- これは試験運用の値であり、品質の転換点ではありません。
- Worker は変更単位 / 検証の収束時に次の段階を評価します。
- 履歴がすでに多く、ファイルやログの一括読み込みや大きなツール出力が予想される場合は、早めに分割して現在の安全な停止点で復旧パッケージを準備し、線に触れてから整理するのではありません。
- 信頼できる読み取り値がない場合は、上記のタスクの段階と予想される入力で停止点を選び、読み取り値は取得不可と明記し、トークンをポーリングしません。
- 処理点に達したか、次の単位が残りを使い切りそうなときは、Worker はツールを収束させ、書き込みを止めて CONTEXT_READY を送り、Owner がネイティブの圧縮を調整します。
- 短いタスクがすでに完了していればそのまま DONE とし、圧縮のために受け入れを削ったり、収束していない操作を中断したりせず、ウィンドウが尽きる直前まで待ちません。
- 圧縮後に新たな実行の進捗がなく入力予算も変わっていない場合は、同じ段階のために整理を繰り返しません。
- ネイティブの自動圧縮がすでに今回の整理を満たしている場合はその証拠を再利用します。

<!-- /role -->
### ユーザー主導の圧縮（全ロール）

- ユーザーが現在のロールのセッションで明示的に圧縮を求めた場合、[long-task](https://github.com/forsakesoul/awesome-skills/tree/main/long-task) Skill（ユーザー定義の圧縮 Skill、プラグインには同梱されません）がインストールされていれば、その自動圧縮の分岐に従って安全な停止点で自ロールの責務、現在のタスク、復旧状態を保存し、このセッションのネイティブ圧縮を一度だけ手配し、完了を確認してから再開します。
- この分岐は Owner による代行を必要とせず、呼び出し元自身の pane/session だけを制御します。
- モデルの自動切り替え、再初期化、リクエスト番号のリセット、待機やブロックの実行への変更、書き込みと通信の許可の拡大は行いません。
- 既存の PAUSED/BLOCKED のリクエストは引き続き有効な Owner の再開制御に従って続行し、復旧パッケージは新たな裁定や許可ではありません。
- 圧縮を明示的に求められていない場合は上記の方針を続けます。
- サポートがない場合は復旧パッケージを保持し、手動のネイティブ圧縮の入口を報告し、成功を装いません。

<!-- role:owner,worker -->
### 責務の保全

- Owner は確定した引き継ぎパッケージと復旧パッケージに、次の要素で書いた責務カプセルを保存します：唯一の writer（複数の Worker がいる場合は、自分に確定した範囲の唯一の writer）、Owner が確定した範囲での実装・テスト・セルフレビュー、無関係な変更の保護、方針の衝突は Owner が裁定、通信プロトコルに従った実際の報告、commit/push/外部送信の許可の境界の維持、Agent を派生させない。
- さらに現在有効なタスクの権威ある seam、不変条件、適用される規約、完全な受け入れ基準、完了 / 残りの項目、次の操作を添えます。
- カプセルには初期化の待機指示を含めず、再開を「続けて」だけで送ってはならず、モデルやロールインスタンスの変更、リクエスト番号のリセット、writer の Owner/Advisor への変更をしません。
- ネイティブの自動圧縮や主導的な整理を経た Worker は、再開後にまず責務カプセル、最新の有効な引き継ぎ、取り消し / 無効の記録、作業ツリーの証拠を読み取り専用で確認します。
- 欠けていれば BLOCKED として証拠を補い、圧縮の要約から責務を推測したり受け入れを落としたりしません。
- カプセルは必要なルールと証拠の場所を保ち、履歴ログ全体をコピーしません。
- 整理は実装の代わりにはならず、タスクの完了を主張できません。

<!-- /role -->
### 復旧情報

- すべてのロールは、ネイティブの自動圧縮、主導的な整理、セッションの復旧の際に、現在の task_id、ロールインスタンス、報告待ちリスト（reply_state、最新の有効な報告、再開 / 補報リクエストの req を含む）、現在の一時停止 / ブロックイベントの req、消費済みの再開 req とその resumes、取り消しの意図と書き込み停止の証拠、取り消し制御の req、取り消しマークと無効にした指示、代理受信の記録、READ_PENDING/RELAY_PENDING の完全な内容と処理済みの req を保持します。req の連番と delivery はタスクディレクトリの台帳が正であり、復旧時はまず状態コマンドを実行して確認します。
- Worker は CONTEXT_READY でさらに責務カプセル、チーム / 有効な引き継ぎのバージョン、元の実行リクエスト番号 execution_request、cwd/ブランチ/HEAD、確定した範囲と許可、受け入れと不変条件、既存変更の保護、完了 / 残りの項目、失敗と検証の証拠、次のステップを添えます。
- 認証情報や再生可能なリンクは含めません。
- Owner は完全な復旧情報を保持してから圧縮します。
- 再開ではまず識別と記録を確認し、圧縮、修正、TEAM_UPDATE によってリセットしません。

<!-- role:owner -->
### Owner による圧縮

- タスク / server / Worker の名前→pane、エンジン、書き込みの停止と idle/done、入力欄が通常の編集状態であることを確認したら、圧縮前のイベントまたは出力の境界を記録します。
- Codex、Claude Code（cc/ccenv）、Pi のネイティブ /compact は Owner が単独で一度だけ送信します。
- 例：herdr agent prompt "<実際の Worker 名>" '/compact' --wait --timeout 120000。
- working/blocked/unknown の Worker にはコマンドを送らず、Worker に通常の返信で圧縮を装わせません。
- 送信の成功や idle は圧縮の完了を証明しないため、初回の経路は実行時に検証しなければなりません。
- get/read で今回のネイティブの完了出力または圧縮イベントを確認し、失敗 / タイムアウトの場合はまず元のエラーと状態を補って読み取り、盲目的に再送せず、復旧情報を保持して再開を待ち、セッションを自動でクリアしたり Worker を置き換えたりしません。
- 完了を確認したら、Owner は元の整理リクエストに関連付けた新しい一意のリクエスト番号で、有効な引き継ぎパッケージ、責務カプセル、復旧情報（取り消しマークと無効にした指示を含む）、最新のチーム、resumes=現在の CONTEXT_READY 通知の req、execution_request=元の実行引き継ぎメッセージの req を付けて [CONTEXT_RESUME] を送ります。
- Worker の完了や停止点は常に responds_to=execution_request とし、再開メッセージや途中の質疑には関連付けません。
- まず責務、取り消しの状態、resumes、識別、バージョン、git status/diff/HEAD が一致することを読み取り専用で再確認してから続行し、ずれがあれば BLOCKED とします。
- サポートされていないエンジンは復旧情報を保持してギャップを説明します。
- 独立した新しいタスクは、前のタスクを引き渡した後に Owner が新しいセッションと完全な初期化を手配し、古いタスクの履歴を自動で再利用しません。
- 整理リクエストごとの圧縮は最大一度で、停止点の準備中にネイティブの自動圧縮がすでに起きていれば、まず今回のイベントと現在の使用量を確認してその結果を再利用します。
- 圧縮後も信頼できる読み取り値が処理の閾値を超えている、または空きが増えていない場合は Owner が裁定し、圧縮をループさせません。
- 使用量が取得できなければギャップを明記します。

<!-- /role -->
## 配信・受信・巡回

<!-- role:worker -->
### Worker の送信

- 実行、修正、コンテキストの停止点の NOTICE は既定で reply_to=Owner とし、局所的な非同期リクエストは添付された reply_to に報告します。
- 配信待ちに従って実際の受信者を確認します。
- 受信者が Owner で working であり、空いている独立 Advisor がいる場合に限り、Advisor に送り先を変えられます。
- その場合は --set relay_to=<Owner のメンバーキー> を付けて代理受信と Owner への転送を明記し、両方に同時に送らず、代理受信の記録（実際の名前、インスタンス、通知の req、最終的な受信者、送信の証拠）を残します。
- それ以外の場合は実際の受信者を有限時間だけ待ちます。
- Worker は唯一の writer であり続けます（複数の Worker がいる場合は、自分に確定した書き込み範囲に限られます）。Advisor の局所的な検証リクエストは Owner の確定した実行引き継ぎパッケージの代わりにならず、変更範囲を広げません。

<!-- /role -->
<!-- role:advisor -->
### 独立 Advisor の代理受信

- 代理受信と明記された NOTICE を受け取ったら読み取り専用を保ち、配信待ちに従って確認し、Owner を有限時間だけ待ちます。
- 送信できるときは --resend <Worker の通知の req> --to <Owner のメンバーキー> で一度だけ転送します。元のリクエスト番号、from、responds_to、引き継ぎバージョン、status、Worker の通知の全文は変わらず、ヘッダーに relayed_by が加わります（これが RELAY_NOTICE です）。
- 利用できない場合は通知の全文を保持して RELAY_PENDING とします。
- Worker に ACK を送らず、自分で裁定したり最終レビューを始めたりしません。

<!-- /role -->
<!-- role:owner -->
### Owner の受信

- 報告ループに従って NOTICE/RELAY_NOTICE を待ち、未読分を読み取ります。
- 業務の task_id、現在有効なバージョン、from と responds_to（報告待ちリストの元のリクエストと予定の受信者に対応している必要があります）を確認し、引き継ぎバージョンだけで進めてはいけません。
- 一致しない通知は履歴の証拠としてだけ扱います。
- 古い形式で関連フィールドが欠けている場合は、確認済みの送信元と引き継ぎの記録からまず証拠を補い、関連付けられなければ BLOCKED とします。
- 実行 / 修正の引き継ぎに対する Worker の DONE だけが、実際の diff と受け入れの確認およびその後のレビューを引き起こします。
- Advisor の回答は対応する設計 / レビューのリクエストを完了させるだけで、同じレビューを再度起こしません。
- CONTEXT_READY は圧縮フローに従って整理と再開を行い、元の実行リクエストは引き続き報告待ちです。
- BLOCKED はまず問題を裁定し、範囲 / 方針 / 受け入れが変わる場合は新しいバージョンを確定します。
- 人によるレビューポイントがなければ許可された後続作業を続け、「受け取りました、ユーザーの続行指示を待ちます」で止まりません。

<!-- role:owner -->
### 実行の巡回（Owner）

- Worker または Advisor の単一のリクエストが 30 分を超えて working のままの場合、Owner は報告を受け身で待つだけでなく、能動的に介入しなければなりません。
- リクエストを送るときに、ホストが対応する定時起動またはバックグラウンドのタイマーで 30 分のチェックポイントを設定します。
- その時点でまだ working なら、その pane とログ / 成果物を読み取り専用で get/read し、脱線していないかを判断します：固定の長い sleep での空待ち、同じ失敗の繰り返しの再試行、誤った読み込みや範囲の拡大、検証結果が 0 件なのに合格扱い、確定した引き継ぎからの逸脱、無関係な方向での消耗。
- 脱線していなければ確認結果を記録して次の 30 分のチェックポイントを設定します。
- 脱線していれば修正します：まず herdr pane send-keys <pane> esc で現在の空転や誤ったツールを中断し（このチームのロールだけを中断し、ユーザーの pane には触れず、pane を閉じません）、idle になったら送信コマンドで新しい req の修正メッセージを一つ送り、観測した証拠、止めるべきやり方、正しい次のステップを書き、確定した範囲は変えません。
- 範囲や方針の変更が必要な場合は置き換えのフローで新しいバージョンを確定します。
- 修正では承認を代理で答えたり、Worker の代わりにコードを書いたり、リクエスト番号をリセットしたりしません。

<!-- /role -->
<!-- role:advisor -->
### 独立 Advisor の出力

- 設計、局所的な回答、最終レビューは同じ報告ルールに従い、リクエストの sync/async に従って reply_to に返します。
- 妥当な問題がなくても明確に報告し、修正提案がないからといって省略しません。
- 状態通知としてだけ受け取った NOTICE には ACK を返さず、通知同士が互いに引き起こし合うのを避けます。

## タスクディレクトリとチーム変更

### タスクディレクトリ

- 上のマッピングにタスクディレクトリが示されている場合、送信コマンドは <タスクディレクトリ>/<task_id>/ の下に各メッセージを 1 ファイルとして書き（<ロールインスタンス>-<連番>.md。先頭にメッセージヘッダーと関連フィールド、その後に本文全体）、台帳も管理します。
- task_id には英数字、ドット、アンダースコア、ハイフンのみを使います。
- 本文は下書きファイルとして書き、--file で送信コマンドに渡します。Owner の引き継ぎパッケージは本文に引き継ぎバージョンを明記し、--set handoff=<引き継ぎバージョン> を付けます。
- メッセージファイルは書いた後は変更せず、修正は新しい送信で行います。
- 受信者に届く prompt にはメッセージヘッダー、関連フィールド、file=<パス> だけが含まれ、受信者は完全なファイルを読んで初めて完全な結果を得たことになります。
- タスクディレクトリはプロジェクトファイルではなく、diff・コミット・レビュー範囲に入りません：Advisor はプロジェクトファイルに対しては読み取り専用のままです。
- Worker が（自分に確定した範囲内で）唯一のプロジェクトコード writer である制約は変わりません。
- ファイルには認証情報、Cookie、Token、再利用可能なリンクを含めません。
- 補読、RESULT_REPLAY、圧縮後の復旧、および途中で参加または交代したロールは、他のロールに求める前に、まずこのサブディレクトリの最新の有効なファイルと状態コマンドの出力を読みます。
- マッピングにタスクディレクトリがない場合、送信コマンドは使えません：本文を herdr agent prompt にインラインで書き、req が一意に増えることを自分で保証し、delivery を記録します。

### タスクディレクトリの削除

- タスクの完了は削除の許可ではなく、どのロールもタスクディレクトリやその中のファイルを自分の判断で削除しません。
- Owner はタスクの納品時にそのタスクサブディレクトリのパスを 1 回報告します。
- ユーザーが削除してよいと明示した後にのみ、マッピングにある削除コマンド（<task_id> を実際のディレクトリ名に置き換える）を実行し、rm で直接削除せず、ユーザーが明示的に求めない限り --force も付けません。
- WAITING/PAUSED/BLOCKED のリクエスト、READ_PENDING または RELAY_PENDING が残っているタスクは削除せず、まず障害点を説明します。

### チーム変更

- ユーザーはタスクの途中で独立 Advisor を追加・削除したり、Worker / Advisor を交代させたりできます。
- 在籍ロールは [TEAM_UPDATE] を受け取り、team_rev が最大のものに従って名前→pane のマッピング、メッセージインスタンス、分担を更新します。
- これは制御メッセージであり、番号を付けず、ACK を返さず、task_id、引き継ぎバージョン、凍結範囲、権限を変更しません。
- 交代または削除されたインスタンスは「停止済みインスタンス」に列挙されます：新しい依頼や再開指示を送らず、遅れて届いた報告は履歴の証拠としてのみ扱います。
- 停止済みインスタンス宛ての未決リクエストは、Owner がその書き込み停止を確認したうえで置換フローにより SUPERSEDED と記録し、新しい req で新しいインスタンスに自己完結した引き継ぎを送ります。
- 新しいインスタンスはマッピングの新しいインスタンス番号を使い、連番は 000 から始め、旧インスタンスの隠れたコンテキストを引き継ぎません。
- Advisor が削除された後、独立 Advisor が残っていない場合に限り、Owner が独立 Advisor なしの規則に従ってレビューを担います。
